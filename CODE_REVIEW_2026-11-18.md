# cardBot code review — 2026-11-18

Reviewed `scratch` at `2c2c7de`: the Go packages from CLI to card history, platform backends, login/daemon and updater, relevant tests, shell scripts, Makefile, and CI/release workflows. File/line references below are to **that revision**, before the tutorial comments. This pass changes comments and documentation, not behavior. For how the parts fit together, start with the [code guide](CODE_GUIDE.md); open work is tracked in [TODO.md](TODO.md).

**Fix the success signal first.** The per-file publication path has useful safeguards: an exclusive partial, optional byte comparison before publication, and a no-replace commit. But “the files in this plan finished” isn't the same as “the requested files on this card were backed up.” The first two findings produced successful results on tiny fixtures where a destination file was missing or too short. No architectural rewrite is needed to address them.

## P1 — data integrity and preservation

### R1. An incomplete walk can produce a successful “All files” receipt

[`PlanCopy`](cardcopy/copy.go) (178–204) continues past directory-read errors and silently drops `DirEntry.Info` failures. [`copyFiltered` / `handleCopySuccess`](app/commands.go) (159–163, 311–332) sends walk warnings only to the log, then writes a verified receipt and marks the mode complete on a nil copy error. The same session will refuse another `all` attempt.

**Observed:** two synthetic photos in different directories, one directory unreadable: `FilesCopied=1`, one warning, **nil error** from `cardcopy.Run`. The receipt consequence follows from the app success path. This isn't a request to treat missing EXIF as a failed copy. An unreadable subtree is different: its contents aren't known. Stop planning on inventory I/O failures, or surface an explicit incomplete outcome that cannot mark the mode complete. Cover both the planner and the absence of a success receipt. Also surface incomplete *analysis* when ratings/dates determine a selection ([`collectMediaFiles`](analyze/analyze.go), 283–313).

### R2. A size-mode skip doesn't recheck the source size

[`Execute` / `classifyDestination`](cardcopy/copy.go) (470–483, 650–656) reclassifies skips, but compares the **current destination** against the **planned source length**. Size mode returns without inspecting the current source. A video that grows while a long plan is being processed can be counted as already copied even when its length no longer matches.

**Observed:** planned a skip at 3 bytes, grew only the source to 6, then called `Execute`: `FilesSkipped=1`, `BytesSkipped=3`, **nil error**. Re-stat the source as a regular file and check its live length before crediting a size skip. Extend [`TestExecute_RevalidatesSizeSkips`](cardcopy/safety_test.go), which changes the *destination*. Size mode needn't become a hash or byte comparison.

### R3. A copy ID identifies a worker, not the mounted source

[`handleCopyDone`](app/commands.go) (180–203) guards against stale workers and a removal **already processed** by the event loop. But the polling detector tracks paths, [`copyFileCtx`](cardcopy/copy.go) (694) opens each source by pathname, and [`dotfile.Write`](dotfile/dotfile.go) (160 onward) resolves the card path again. If a different card occupies the same mount path before a removal is observed, later reads or the receipt can belong to the replacement. Even `full` checks bytes from the file that was actually opened, not that it came from the analyzed volume.

There is also a mismatch in the other direction: [`normalizeCardPath` / `sameCardPath`](app/path.go) only clean the string. A **relative CLI target** and the detector's absolute path to that same card compare unequal; [`handleRemoval`](app/handlers.go) (268) can miss the active copy. Capture a canonical path and directory identity at acquisition, bind source reads and history to that card, and fail closed if it changes. Test relative-target removal and replacement at a reused path with private directories and a fake detector. This is a source-read finding, **not** a claimed live hot-swap test.

### R4. The “destination outside card” check compares spellings, not directory identities

[`normalizeCopyRoots` / `isSameOrWithin`](cardcopy/copy.go) (538–595) resolve symlinks and use `filepath.Rel`. On a case-insensitive macOS filesystem, two differently cased paths can name the same directory; resolving Unix symlinks does not canonicalize that case. A destination on the card can consequently pass as a separate backup location. [`destinationLocation.open`](cardcopy/destination.go) pins the chosen destination, but doesn't establish that it was off-card to begin with.

Compare the source directory identity against the existing destination ancestors before allowing creation. Don't lowercase all paths or reject all directories on the same filesystem: distinct case-sensitive directories and ordinary folder-based ingests must still work. Add filesystem-aware coverage for both existing and not-yet-created destination bases. This assessment is from source inspection, not a test on camera media.

### R5. Explicit setup can overwrite a config it couldn't read

[`config.LoadWithStatus`](config/config.go) (133–140) returns an error and an empty status for a non-missing read failure. [`runInteractive`](cmd/root.go) (275–322) falls back to defaults and, for `--setup`, refuses only `LoadMalformed` and `LoadUnsupported`. If the file is unreadable but its parent directory is writable, the atomic save can rename defaults and new answers over recoverable settings. Separately, on a **failed** setup save the caller still synchronizes the LaunchAgent and prints “Setup saved.”

Allow setup persistence only after a successful load with a known valid/missing status. Don't apply login changes or claim persistence after a failed save. Test read failure and save failure independently with a fake setup/launcher; neither needs a native picker or a live login agent.

## P2 — user-visible correctness and lifecycle

- **R6 — One-run overrides can become permanent.** [`runInteractive`](cmd/root.go) (297, 421–440) applies `--dest` / `CARDBOT_*` to `cfg`, then saves that *whole object* to record `LastSeenVersion`. This affects a valid config on the first version stamp or version change, not every launch. A one-off destination or verification override can become the next run's default. Stamp the saved settings, not the effective runtime copy. Test a version change with an override: the app should use the override, but only the metadata should change on disk.
- **R7 — A selected sidecar can be filed apart from its photo.** [`PlanCopy`](cardcopy/copy.go) (259–282, 329–333) gives companions the earliest primary's date/time even when that primary wasn't selected. Primaries keep their own timestamps. **Observed:** given a same-stem JPEG dated April 1 and NEF dated April 2, selecting just the NEF put its XMP under April 1 with the JPEG's timestamp stem, and the NEF under April 2. Both had sequence `0001`; photo software still cannot pair them by name. Define a consistent date/stem for the asset across filters, accounting for existing names. Test all vs. selects with different primary timestamps, not just a single primary and sidecar.
- **R8 — Observed card transitions can be dropped or delivered out of order.** Both release pollers ([macOS](detect/detect_darwin_nocgo.go), 139–166; [Linux](detect/detect_linux.go), 177–211) update tracking even if a nonblocking send hits a full channel. Later polls don't retry that transition. Also, arrivals and removals use *different* channels; when both are pending, the app/daemon `select` need not consume them in observation order. A removed card can remain current, or a present one never be offered. Deliver ordered transitions or reconcile snapshots, with shutdown able to interrupt a blocked sender. Test a slow consumer, a burst, and remove/reinsert without scanning host mounts.
- **R9 — A late scan failure can finish the wrong card.** [`displayCard`](app/handlers.go) (158–180) checks cancellation and then, on a general analysis error, calls unqualified `finishCard()` from the scan goroutine. If the loop moves on in between, `finishCard` clears the *new* card and cancels its scan. The success path checks a path, not a scan generation. Gate scan outcomes and state changes on the same session under the same lock, or deliver tagged outcomes to the loop as copy already does. Test delayed success/error after switching cards, including a reused path. This is an ordering issue, not a reported Go data race.
- **R10 — Login commands can claim a state they didn't establish.** [`runInstallDaemonCommand`](cmd/daemon_cmd.go) (106–126) bootstraps and starts the KeepAlive job *before* saving/checking daemon preferences. With a malformed config the headless process refuses to start, but [`updateSavedDaemonPrefs`](cmd/daemon_helpers.go) only warns; the install command can report success and leave launchd retrying. In reverse, [`uninstallWith` / `statusWith`](launch/agent.go) (96–116) ignore all bootout errors, remove the plist, then treat a missing plist as an unloaded job. Preflight the config, propagate partial failures, and distinguish “not loaded” from “couldn't unload.” Cover both with the existing fake launchctl seam.
- **R11 — Relative install records depend on the *uninstaller's* working directory.** [`install.sh`](scripts/install.sh) (194–197, 224) records the install-dir spelling. [`uninstall.sh`](scripts/uninstall.sh) (214–218) interprets it in its current directory. After an install to a relative directory, cleanup from elsewhere can miss the install or remove a *different genuine cardbot*, which also passes the version check. Record an absolute path on install; don't guess the location of legacy relative records. Use two temporary working directories and stub binaries for regression coverage.
- **R12 — `--daemon --dry-run` doesn't make the launched session a preview.** [`NewRootCommand` / `runInteractive`](cmd/root.go) accept the two flags together, but branch to `runDaemonCommand(cfg, logger)` before using `opts.DryRun`. The [launch callback](cmd/daemon_cmd.go) doesn't pass that flag to the child. The watcher itself copies nothing, but a copy choice in the window it opens writes real files. Reject the combination with a clear message, or deliberately propagate preview mode to every supported launch path. Test flag validation or a fake launch, not a live daemon.

## P3 — progress feedback

- **R13 — A large movie gets no mid-file progress updates.** [`Execute`](cardcopy/copy.go) (453, 485–525) resets an atomic counter and [`trackingReader`](cardcopy/reader.go) increments it, but no production progress sample reads it. Callbacks sample before files and at the end; the UI's two-second throttle isn't a timer that creates samples. A single long transfer can look idle until it finishes. Emit bounded samples during streaming, keeping bytes read distinct from files committed. Test with a paced reader and injected clock rather than a multi-GB fixture.
